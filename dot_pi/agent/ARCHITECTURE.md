# Custom Pi UI architecture

## Ownership and dependency direction

- `themes/catppuccin-latte.json` owns raw house colors. `extensions/ui/design-system/palette.ts` reads its `vars`; there is no second hex table.
- `extensions/ui/design-system/theme.ts` maps colors to semantic roles and styles. The custom UI intentionally keeps the existing fixed Latte appearance; runtime theme switching is not implemented here.
- `extensions/ui/design-system/terminal-color.ts` owns color parsing, blending and nested ANSI styling. Footer quota ramps use the same blending implementation.
- `extensions/ui/terminal-text.ts` owns clipping, wrapping, column slicing and hanging-indent policy. Pi TUI owns Unicode/grapheme measurement and escape parsing; do not maintain another tokenizer or width table locally.
- `extensions/ui/align.ts`, `frame.ts`, and `selection-marker.ts` own shared spacing, rounded/square frames, focused-row bands and selection contrast. Frames compute clipping and padding themselves; callers provide content and spacing insets rather than precomputed width metrics.
- `extensions/ui/editor-decorator.ts` composes per-extension editor decorators exactly once per session_start, chaining on pi's `getEditorComponent`, and owns the base editor factory (`createDefaultEditor`). Only the first registered decorator builds that base editor, and extensions load in filesystem order, so every caller passes this factory instead of constructing its own. Decorators rebind instance methods (the sanctioned adapter hook) and accessor-intercept reassignable callbacks, because pi reassigns `onChange`/`onSubmit` after the editor factory runs; management of that contract lives here, not per extension. A decorator that renders dynamic content also receives the live TUI, so it can request its own repaints. It also owns `EMBEDDED_LOADER_FIELD_WIDTH`, the top-border columns reserved for the embedded loader, so decorators drawing beside the loader lay out against a stable field.
- Questionnaire and footer modules own their domain content and interactions, not parallel UI engines. Shared `ui/` modules never import extension-specific modules and have no `index.ts` extension entry point.
- `extensions/model-fallback/` owns the unified model surface (`/models`, alias `/fallback`): the chain decision logic (`chain.ts`, `fallback-session.ts`, `failover.ts`, `taxonomy.ts`, `config.ts`) and the picker that presents it. `model-catalog.ts` builds the rows from the available catalogue plus the session scope, `model-price.ts` owns what a row costs and `model-price-gauge.ts` the gauge, and `openrouter-pricing.ts` owns the live public OpenRouter price list the picker prefers for OpenRouter rows (catalog zeros there mean unpriced, never free); `model-picker-state.ts`, `model-picker-view.ts`, `model-picker-line.ts`, `model-picker-list.ts`, `model-picker-tabs.ts`, `model-picker-groups.ts`, `model-picker-window.ts`, `model-picker-commands.ts`, `model-picker-editor.ts` and `model-picker-render.ts` hold the pure state and layout (group dividers, the agent editor and row actions included), `model-picker-component.ts` is the pi-tui keyboard/mouse adapter, and `picker.ts` is the flow. `model-picker-settings.ts` reads the settings the `subagents` package owns and writes back exactly one thing: the inline editor's model and thinking for one agent in `subagents.agentOverrides` (whole-file read-modify-write, unrelated keys and the file's own indentation preserved, atomic replace). The scope is reported, not edited - `/scoped-models` is a built-in interactive command that pi dispatches only from its own editor, so the scope tab names it instead of pretending to open it; `/subagents` stays the advanced per-agent surface, dispatched only after the picker's modal is released and only when that command is registered. Escape in the picker is one level back at a time (search, open editor, committed row action, then close), and the footer states which one is next.
- `extensions/footer/nebius-session.ts` and `inco-session.ts` are the config's browser-session boundaries: neither Nebius nor Inco publishes a balance API, so each replays the console session of the machine (Nebius' gateway chain; Inco's Clerk handshake plus the console layout's flight payload). `quota-nebius.ts` and `quota-inco.ts` parse those payloads (pure, fixture-tested); `nebius-cookies.ts` owns the macOS Chromium cookie format and `safari-cookies.ts` the Safari one. The Chromium read comes from the profile declared in `~/.pi/web-search.json`, the Safari read is the Inco console's store; sessions are read, never written, no other module reads browser cookies, and nothing here runs from a render path.
- `extensions/renderers/` owns presentation of assistant responses, all Pi tool-execution rows and compaction cards. Tool-specific vocabulary lives in `tool-presentation.ts` (Pi's own tools) and `package-presentations.ts` (tools registered by packages); unknown and late-loaded tools use the generic humanized fallback. It never registers, replaces, or executes a tool. Edit/write and any result carrying native images use standalone panels on the shared content column, with a dedicated inline/expanded code view for applied changes; other expanded content stays with the originating tool extension.
- `ui/activity-line.ts` owns the tool/count identity, the shared content column every surface aligns on, task hierarchy, status glyphs and rail ink; `ui/activity-timing.ts` owns responsive duration/timeout/failure formatting at the right. `ui/activity-details.ts` owns the detail gutter and coordinate translation. `ui/change-block.ts` owns numbered code rows and pastel diff washes. `ui/tool-panel.ts` owns the standalone panel frame shared by file mutations and image captures: uppercase heading, status/timing strip, unclipable native payload lines and native fallback coordinates, using `ui/frame.ts` insets. Panel-border and diff-background roles live in the semantic theme. They reuse Pi's wrapping/measurement, not another text engine.
- `renderers/tool-changes.ts` owns applied mutation presentation. `change-document.ts` translates Pi's numbered edit diff and uses Pi's public diff generator for observed writes; it never reimplements matching or LCS. `tool-mouse-surface.ts` is the version-bound mouse adapter: a synthesized click anywhere on an applied mutation toggles preview/full view symmetrically. Press/drag/release are not treated as clicks. Standalone mutation panels interrupt ordinary tool chains rather than inheriting their rail.
- `container-sandbox/` owns the Apple container routing for this config: `session.ts` holds the per-session runtime, prompt suffix and `/container`; `wt.ts` is the only reader of the wt registry (`wt list --json`, `wt sync`); `container.ts` is the only caller of the `container` CLI (`exec`, `stop`, address); `bash-ops.ts` owns host-to-guest path mapping and the `BashOperations` adapter. It never creates, names or removes containers, and file tools stay host-side because the worktree is the same bytes through the mount.
- `ui/pi-runtime.ts` resolves the CLI's actual bundled classes and owns the shared supported-version gate. `ui/pi-component-patch.ts` owns checked method replacement and restoration. Private Pi field/method knowledge stays at the display-surface boundaries; both `renderers/` and `raw-transcript/` check the runtime version before installation rather than silently leaving an unsupported runtime partially styled.
- `renderers/response-message.ts` classifies response sections using provider phase metadata and message lifecycle, never prose heuristics. `assistant-surface.ts` alone adapts Pi's assistant component, including streaming flags, thinking controls, stop notices and Markdown transformers. It rebuilds independently of the retired raw assistant patch so the first reload can migrate already-loaded classes.
- `ui/response-divider.ts` owns centered response landmarks and fades; `ui/response-markdown.ts` owns readable typography, inset, width bounds and Markdown caching over Pi's parser. `ui/relay-line.ts` colors authored rail glyphs in plain text tokens, not code fences.
- `raw-transcript/` owns literal user prompt frames and the skill invocation callout. `prompt-block.ts` composes attachment content before source text; `skill-block.ts` paints the rose callout band from the parsed skill block and `skill-surface.ts` mounts it on Pi's skill component while retaining the global expand toggle and adding the click-to-fold gesture the native card never had; its rose glow easing to transparent is static paint computed per render, never a timer, and the band owns its own viewport painting instead of Pi's flat custom-message background. `surfaces.ts` preserves that component across native rebuilds and retains prompt zones. `attachment-surface.ts` adapts Pi's entry mounting to move a matching attachment entry into the nearest prompt, retaining native entry invalidation/theme rebuilding without its standalone spacer. `ui/prompt-attachment.ts` is the cross-extension marker/ownership contract; `extensions/attachments/` (no index.ts: shared library) owns the scenario-neutral capture machinery - alias ingestion, editor hooks, thumbnail strip, previews and snapshot records - and `prompt-attachments/` owns only the prompt wiring (draft lifecycle, its session entry, strip widget). The questionnaire reuses the same machinery through `questionnaire-captures.ts`, answering with its own reference rule: its split text (answers, drafts, live editor) retains captures, submits them as multimodal result content and persists tile-sized snapshot records in its details. Assistant content, tool spacing and mouse geometry belong to `renderers/`, so two extensions never patch the same surface.

## State lifetime

- Each questionnaire dialog owns its editor, navigation state, response collection and render cache. Keyboard events drive mutations on the TUI event loop; render functions only read domain state. The Pi editor computes its own layout during rendering.
- `QuestionnaireResponses` owns answers, drafts and multi-selection sets. Navigation owns the current tab/cursor; selection transitions operate through those owners. Plain snapshots cross the chat-pause boundary.
- The tool registration owns the map of chat-pause snapshots. It deletes a snapshot on completion/cancellation and clears the map on session shutdown, including reload.
- Pi owns tool execution, results, images and expansion state. `ToolRow` owns presentation state; `ToolLifecycle` records starts only while execution is actually pending, then freezes completion time. `tool-durations.ts` remembers measured durations in a reload-stable weak cache keyed by result-content identity and call ID. Pi keeps those content arrays during `/reload`, so remounting retains real timings without altering results or writing extra session entries. Freshly loaded history without an observed duration remains unknown. Render methods only read this state; observations and cache writes happen during native display updates.
- `write-snapshots.ts` reads bounded regular-file before-images during `tool_call`, then records successful comparisons at `tool_execution_end` before Pi updates the row. Arguments, results and execution are never replaced. Pending captures clear at agent end/shutdown; a generation check rejects late reads after clearing. Completed views use weak result-content/call-ID keys across reload, without extra session entries. Unknown, binary, oversized or specially normalized baselines fall back to explicitly labeled neutral written content (or native details), never invented removals/additions. Rendering performs no filesystem IO.
- Assistant response dividers and Markdown cache by width and invalidate with their owning message. Streaming rebuilds presentation only; stored messages and provider signatures are untouched. Unknown streaming responses remain neutral until completion; explicit provider phases distinguish commentary and final text even within one message. No response animation timer is introduced.
- One session-scoped `ui/activity-clock.ts` lazily repaints live tool rows, deduplicated per TUI. The final completion stops its pulse; shutdown/reload disposes it and restores the display adapters. Native detail renderers retain separate call/result caches and continue receiving completion after first expansion so their own resources can settle.
- Prompt attachment relocation happens during entry mounting, never during rendering. Session entries and model image content are unchanged; unmatched entries remain visible standalone. Nested entries retain their native invalidation lifecycle, and prompt/attachment display patches restore together on shutdown or reload.
- Questionnaire transcript slots share Pi's row-local answered flag. Their invalidation is queued to avoid synchronous render reentry. Capture pruning runs outside the store's own repaint path: the dialog effects batch prunes once, the strip only invalidates, so a no-op prune never loops a render.
- `prompt-telemetry` owns the prompt it tracks, the activity block it draws in the editor's top border, and its lifetime: the block renders from that state plus the current clock, with no tick timer and no retire timer of its own. Its numbers and tally icons wear the loading color while their words stay muted house ink, its elapsed track carries the prompt border hue, and before the first count the track sweeps the columns the readings will take - so the block reports and waits at one width, and a settled block stays frozen until the next prompt.
- `ui/surface.ts` owns widget registrations and subscriber notifications. `ui/ordered-widget-stack.ts` is the Pi mounting adapter, not another renderer or color system.

## Boundaries and verification

- `schema.ts` owns every tool-data shape: the LLM input schema and the canonical domain/`details` schemas; UI domain types derive from them via `Static`, so each field has one declared rule set. `normalizeQuestions()` enforces semantic constraints beyond shape (trimming, `Q{i}` fallbacks, uniqueness), and session replay re-validates through the same schemas (`Value.Parse`/`Value.Default`), falling back to plain text when the payload is unusable. Pending streamed previews read only the labels they display.
- Public output is bounded by terminal columns, not JavaScript string length. Editor rendering reserves enough space for a wide grapheme and cursor before the frame clips narrow viewports.
- Regression tests cover multiline/editor alignment, Unicode, styled wrapping, hyperlinks, narrow frames/surfaces, selection markers and footer color interpolation. They use Pi's real editor without starting terminal IO.
- Run the lint, type-check and test scripts from this directory. Format only changed code files. Use `/reload` and a visual questionnaire check after UI changes; automated tests do not establish font-specific appearance.
