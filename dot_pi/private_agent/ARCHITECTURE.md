# Custom Pi UI architecture

## Ownership and dependency direction

- `themes/catppuccin-latte.json` owns raw house colors. `extensions/ui/design-system/palette.ts` reads its `vars`; there is no second hex table.
- `extensions/ui/design-system/theme.ts` maps colors to semantic roles and styles. The custom UI intentionally keeps the existing fixed Latte appearance; runtime theme switching is not implemented here.
- `extensions/ui/design-system/terminal-color.ts` owns color parsing, blending and nested ANSI styling. Footer quota ramps use the same blending implementation.
- `extensions/ui/terminal-text.ts` owns clipping, wrapping, column slicing and hanging-indent policy. Pi TUI owns Unicode/grapheme measurement and escape parsing; do not maintain another tokenizer or width table locally.
- `extensions/ui/align.ts`, `frame.ts`, and `selection-marker.ts` own shared spacing, rounded/square frames, focused-row bands and selection contrast. Frames compute clipping and padding themselves; callers provide content and spacing insets rather than precomputed width metrics.
- `extensions/ui/editor-decorator.ts` composes per-extension editor decorators exactly once per session_start, chaining on pi's `getEditorComponent`, and owns the base editor factory (`createDefaultEditor`). Only the first registered decorator builds that base editor, and extensions load in filesystem order, so every caller passes this factory instead of constructing its own. Decorators rebind instance methods (the sanctioned adapter hook) and accessor-intercept reassignable callbacks, because pi reassigns `onChange`/`onSubmit` after the editor factory runs; management of that contract lives here, not per extension. A decorator that renders dynamic content also receives the live TUI, so it can request its own repaints. It also owns `EMBEDDED_LOADER_FIELD_WIDTH`, the top-border columns reserved for the embedded loader, so decorators drawing beside the loader lay out against a stable field.
- Questionnaire and footer modules own their domain content and interactions, not parallel UI engines. Every questionnaire choice includes a user-written answer path; the public schema cannot remove it. `ask-user-question/questionnaire-events.ts` is the one cross-extension contract for answer/discussion mode: goal-gate suspends automatic continuation throughout a discussion, resumes only when the questionnaire is explicitly reopened, and treats a questionnaire raised after the latest `goal block` as the visible stop instead of injecting the same question again. Shared `ui/` modules never import extension-specific modules and have no `index.ts` extension entry point.
- `extensions/goal-gate/` owns one session ledger and two routing decisions: `task-routing.ts` asks Jev whether a human prompt requests work, then seeds one request item; `tool.ts` passes declared deliverables and explicitly discovered affected surfaces after discovery, using the ledger count as a proposal and Jev as the final direct/scoped reviewer. An uncertain request stays tracked, uncertain scope prefers scoped, and a Jev outage warns visibly while retaining the ledger proposal. `ledger-edits.ts` permits dismissing a false work request only before any deliverable is declared. `routing-log.ts` records hashed prompts, affected-surface counts and decision metadata in per-session files under `jev/routing/` with 14-day retention; raw prompts and surfaces never enter that log. Child subagents do not own goals.
- `extensions/model-fallback/` owns the unified model surface (`/models`): the chain decision logic (`chain.ts`, `fallback-session.ts`, `failover.ts`, `taxonomy.ts`, `config.ts`) and the picker that presents it. `model-catalog.ts` builds the rows from the available catalogue plus the session scope and owns how a saved `enabledModels` entry names a model exactly (pi's colon-suffix rule, bare ids included), the saved-order sort of the scoped group and the fuzzy search every model list filters with (`filterRows`, pi-tui's `fuzzyFilter`), `model-price.ts` owns what a row costs and `model-price-gauge.ts` the gauge, and `openrouter-pricing.ts` owns the live public OpenRouter price list the picker prefers for OpenRouter rows (catalog zeros there mean unpriced, never free); `model-picker-state.ts`, `model-picker-view.ts`, `model-picker-line.ts`, `model-picker-words.ts` (the three names - session, startup default, Ctrl+P list - that every picker surface spells the same way), `model-picker-effort.ts` (the reasoning column all three model lists share), `model-picker-list.ts`, `model-picker-price.ts` (the session tab's price block), `model-picker-scope.ts` (the scope tab's rows, status lines and row-aware footer), `model-picker-tabs.ts` (the fallback and agent tabs), `model-picker-groups.ts`, `model-picker-window.ts`, `model-picker-keymap.ts` (what one terminal key asks for), `model-picker-commands.ts`, `model-picker-scope-edits.ts` (the saved list's membership, removal and order edits, from the scope tab and the session catalogue), `model-picker-editor.ts` (with `model-picker-editor-rows.ts` - the no-model-change row - and `model-picker-editor-render.ts`) and `model-picker-render.ts` hold the pure state and layout (group dividers, the agent editor and row actions included), `model-picker-component.ts` is the pi-tui keyboard/mouse adapter, `command.ts` registers the `/models` command, and `picker.ts` is the flow. `model-picker-settings.ts` reads the settings the `subagents` package owns and writes back exactly two things: the inline editor's model and thinking (or the agents list's thinking alone) for one agent in `subagents.agentOverrides`, and the saved `enabledModels` list - its membership and its order - both as whole-file read-modify-write (`model-picker-settings-file.ts` owns the file's own indentation and the atomic replace) with unrelated keys preserved, and a refusal when the list another writer owns changed underneath; `model-picker-saves.ts` turns those writes into the notices, which state when each takes effect. `agent-roster.ts` asks the installed `subagents` package for its agent roster over pi's in-process event bus (`pi-subagents:agent-roster:v1`, produced by that package's own discovery) and validates the plain-JSON answer field by field, so the agents tab lists every agent that can be pinned - each row naming its effective model and whether that model is a pin, the agent's own definition, `subagents.defaultModel` or the session's - while a pin left behind by an agent that no longer exists is listed and marked instead of silently doing nothing, and a package that does not answer leaves the picker on the pins it can read itself. The Ctrl+P list tab (labelled `ctrl+p`) lists the entries once with what each resolved to, each row saying `Ctrl+P list`, `in Ctrl+P list via <pattern>` or `not in Ctrl+P list`: enter toggles membership - an exact entry leaves the list, any other model joins it as its own exact entry (a model a saved pattern covers is pinned explicitly, never expanded out of its wildcard) - backspace removes an entry, a wildcard included, as one whole entry the footer labels, and alt+up/down orders the list. The session catalogue's enter adds the highlighted model to that same saved list as its own exact entry and ctrl+x removes that entry again - so a scope can be built from the default picker that has no entries at all - and its ctrl+s saves the highlighted row as pi's startup default (`defaultProvider`/`defaultModel`, the keys pi's own `/model` picker writes with that key), which is a write of its own that names new sessions and leaves the running one on the model it is on; a row the saved list already covers - an exact entry, or a pattern that matches it - is one this session can run, so enter there switches the session model instead, and the row says `in Ctrl+P list` or `in Ctrl+P list via <pattern>`. A row only a pattern covers has no exact entry to remove, so ctrl+x leaves that edit to the scope tab's explicit backspace. Every editing key is a control key (enter, ctrl+x, ctrl+s, backspace) and the session search field owns every printable character: `space` and every letter stay text, so a model id like `codex` or `x-ai/grok` is searchable to its last character. `enabledModels` is pi's own setting, pi resolves the scope at session start, and no extension API can move the running session's scope (`ctx.scopedModels` is a read-only snapshot), so the tab says an edit applies at the next session start and the picker's session list reacts immediately without faking a runtime mutation: the rows follow the saved `enabledModels` order, and a model the saved list names exactly (and this session's own scope does not cover) leaves the `available` rest for the `in Ctrl+P list next session` group the moment the key is pressed - `in Ctrl+P list now` (usable now), `in Ctrl+P list next session` (wanted from the next session on, tagged `not cycling now  in Ctrl+P list`), `available` - so nothing needs a relaunch to show up in the right list, while the session scope itself still moves only at the next session start. A saved wildcard moves whole, is never expanded into ids and is never rewritten by a membership toggle. `/scoped-models` remains pi's own built-in interactive command for the same list - the tab names it instead of pretending to open it, and `command-filter.ts` keeps it, `/model` and `/thinking` out of the slash menu, as it does the `subagents` package's `subagents-models` (whose per-agent mappings the agent tab edits) and two rows that answer nothing here (`subagents-watchdog`, off by default, and pi's bundled `llama`, with no llama.cpp router configured), since pi hardcodes its built-ins and exposes no unregister API: `/models` is the only model entry there, and a hidden command typed out in full still runs; `/subagents` stays the advanced per-agent surface, dispatched only after the picker's modal is released and only when that command is registered. The agents tab shows every agent the `subagents` package reports - its effective model and reasoning column, where left/right writes that one agent's thinking and enter or a click opens the model editor - and keeps a pin whose agent no longer exists visible, marked `no such agent`, so it can be repointed; reasoning levels always come from pi's `getSupportedThinkingLevels` and are clamped by pi's `clampThinkingLevel`, so a model that cannot disable reasoning never advertises off and a non-reasoning model reads as off rather than an invented auto; the inline editor opens on the pinned model, or on an explicit no-model-change row when the override has no model row to sit on (a stored thinking level alone, or a pin the catalogue does not list), shows a stored level the pinned model no longer accepts, marked `unsupported` (a width-safe `!` marker when the column is too narrow for the word), and a save that changes nothing writes nothing. Escape in the picker is one level back at a time (search, open editor, committed row action, then close), and the footer states which one is next.
- `extensions/footer/inco-session.ts` is the config's browser-session boundary: Inco publishes no balance API, so it replays the console session of the machine (Clerk handshake plus the console layout's flight payload). `quota-inco.ts` parses that payload (pure, fixture-tested); `safari-cookies.ts` owns the macOS Safari cookie format and is the only browser-cookie reader. The read is the Inco console's store; sessions are read, never written, and nothing here runs from a render path.
- `extensions/tool-guard/` owns the two refusals the session logs paid for: a host-level `sleep` of ten seconds or more (`blind-wait.ts`), and a bash stage whose work a dedicated tool owns (`shadowed-tools.ts`) - `ls`, `cat`, `head`, `tail`, `nl`, `tac`, `bat`, `grep`/`rg`, `find` and `tree` are refused wherever they sit, because a pipe, a redirect (`2>/dev/null` included) or a `head`/`tail` wrapper changes neither what the call is nor where its text lands. `shell-text.ts` owns the parsing (quotes, heredocs, separators, pipe stages), `stage-arguments.ts` the words of a stage (paths, patterns, count flags, /tmp paths), `suggested-call.ts` the dedicated call the refusal names, and `policy.ts` composes the rules - the one surface `index.ts` and the audit scripts read. It registers no tool and replaces none: the refusal happens at `tool_call`, which covers `bash` and `host` alike before execution, and its exemptions name work no tool can do (counts, `jq`/`awk`/`sed` derivations, `find -exec` and `xargs` mutations, throwaway logs under /tmp, a reader feeding a count or the clipboard) rather than punctuation. It does activate `ls`/`grep`/`find` at session start, but only where `pi.getAllTools()` exposes them, so an explicit `--tools` grant still wins: pi's own prompt sends the model to bash for file operations exactly while those tools are missing (the `Use bash for file operations like ls, rg, find` guideline disappears as soon as one is active), and a refusal that names a tool the session does not have is a dead end.
- `extensions/tool-scope/` owns the session's own active-tool set: which tool schemas a UI session starts without, and the `load_tools` loader that brings one back. `policy.ts` holds the pure plan (config layers, `defer` and `off`); `index.ts` only wires `session_start` and the loader's activation. It scopes UI sessions (`ctx.hasUI`) and never headless or granted sessions, so a subagent child keeps the set its caller granted; tool-guard's additive `setActiveTools` call reads the live set and stays compatible.
- `extensions/workspace/` owns `/workspace`: a wt worktree workspace on a branch, with Pi already running in its herdr pane. `wt.ts` is its only wt caller (`list --json` to find the branch's holder, then `spawn --pane --async` or `switch`), `herdr.ts` its only herdr caller (`api snapshot`, `agent start`, `agent prompt`), `launch.ts` turns a checkout into a running Pi (pane lookup by workspace id then cwd, the first prompt, and the bounded retry a fresh pane needs while its shell prints its banner), `args.ts` the parse, `index.ts` wiring and branch completion. It never focuses the workspace it opens unless `/workspace --focus` asks, because opening one must not move the operator's focus, and its own kill timeout stays strictly longer than the `--timeout` it hands herdr: killing that CLI mid-wait leaves a half-registered agent holding the pane (recovery: `herdr agent get <name>`, then `wt clean`).
- `extensions/simplify/` owns the `/simplify` command: explicit scopes stay deterministic, while `target-routing.ts` asks Jev whether a bare target is a literal file area or a semantic request; uncertain/unavailable decisions and failed literal lookups use `target-message.ts` to hand the entire request to the parent agent for per-unit planning and execution (existing worktree first, temporary worktree otherwise, commit only when requested). The deterministic path runs four fresh-eyes lenses through the installed subagents package, an autonomous pass over provable Git-scoped findings, a human checkpoint for the rest (all direct-target findings included), and the project's own gates after every edit. `index.ts` is wiring only (registration, preflight, notices) and `pipeline.ts`/`pipeline-apply.ts` are the two stages; `command-args.ts` parses flags and free target text while `command-help.ts` owns its help; `git-shell.ts` is the only process boundary, `git-selection.ts` decides which files each mode yields, `git-snapshot.ts` resolves a bare target or explicit `--files`/`--snapshot` roots without Git and recursively excludes dependency/build directories, `git-files.ts` owns the per-file facts (ranges, size, binary/submodule checks, content hash), and `git-scope.ts` assembles the manifest under caps (200 files, 4096 ranges) that refuse rather than truncate; `lenses.ts` owns the four lens tasks, the findings schema and the fanout script it writes for the parent model to launch by path; `turns.ts` resolves a dispatched run on `agent_settled` (never on `waitForIdle` ordering); `capture.ts` reads the `subagent` tool result defensively, field by field; `findings.ts` validates, scope-filters, deduplicates and ranks what the lenses returned, and drops findings whose file changed under it; `verify.ts` detects the project's gates; `apply.ts` carries the behaviour-preservation and verification contract; `select-ui.ts` is the checkpoint dialog; `report.ts` is the notices. The extension never edits code, runs a gate or stages anything: the model does that through its own tools, and the lens children are read-only by contract (`agents/simplifier.md`). The semantic-target handoff asks the parent to apply the same lens and verification contracts per unit, and permits commits only when the user's directive explicitly requests them. Out-of-scope observations are reported as notes, every dropped finding carries its reason, and a missing or unusable lens result is a reported failure rather than an empty finding set.
- `extensions/context-budget/` owns the user-selected prompt-cost ceiling. `budget.ts` defines thresholds, `guard.ts` owns the measured cycle state, `pruning.ts` archives large tool output before replacing only old provider-context copies with recoverable paths and deletes inactive artifact directories after 14 days, `checkpoint.ts` persists bounded goal/usage/file telemetry, `summarizer.ts` contains the only summary-model API boundary and falls back to Pi's current-model compaction, and `settle.ts` invokes that in-session compaction. The summary model is configured in `context-budget.json`; one-off calls disable cache retention and use fresh routing IDs. A cycle succeeds only when the first measured prompt lands at or below half the effective ceiling; it then needs 48k growth and two work turns before re-arming. One stricter recovery may run, after which automation pauses instead of looping. Pi retains 20k recent tokens; the full transcript and custom checkpoint entries remain durable.
- `extensions/settle-handshake/` (no index.ts: shared library) owns the one cross-extension contract on the settle boundary: `context-budget` claims it while threshold or recovery compaction is pending, and `goal-gate` defers continuations without spending its attempt budget. Completion, failure, cancellation, any compaction and session start release the claim; a TTL self-heals a wedged cycle. Extensions load in filesystem order, so the claim makes compaction-before-continuation explicit instead of relying on `ctx.isIdle()`, which cannot arbitrate handlers within one settle dispatch.
- `extensions/renderers/` owns presentation of assistant responses, all Pi tool-execution rows and compaction cards. Tool-specific vocabulary lives in `tool-presentation.ts` (Pi's own tools) and `package-presentations.ts` (tools registered by packages); unknown and late-loaded tools use the generic humanized fallback. It never registers, replaces, or executes a tool. Edit/write and any result carrying native images use standalone panels on the shared content column, with a dedicated inline/expanded code view for applied changes; other expanded content stays with the originating tool extension.
- `ui/activity-line.ts` owns the tool/count identity, the shared content column every surface aligns on, task hierarchy, status glyphs and rail ink; `ui/activity-timing.ts` owns responsive duration/timeout/failure formatting at the right. `ui/activity-details.ts` owns the detail gutter and coordinate translation. `ui/change-block.ts` owns numbered code rows and pastel diff washes. `ui/tool-panel.ts` owns the standalone panel frame shared by file mutations and image captures: uppercase heading, status/timing strip, unclipable native payload lines and native fallback coordinates, using `ui/frame.ts` insets. Panel-border and diff-background roles live in the semantic theme. They reuse Pi's wrapping/measurement, not another text engine.
- `renderers/tool-changes.ts` owns applied mutation presentation. `change-document.ts` translates Pi's numbered edit diff and uses Pi's public diff generator for observed writes; it never reimplements matching or LCS. `tool-mouse-surface.ts` is the version-bound mouse adapter: a synthesized click anywhere on an applied mutation toggles preview/full view symmetrically. Press/drag/release are not treated as clicks. Standalone mutation panels interrupt ordinary tool chains rather than inheriting their rail.
- `container-sandbox/` owns the Apple container routing for this config: `session.ts` holds the per-session runtime, prompt suffix and `/container`; `wt.ts` is the only reader of the wt registry (`wt list --json`, `wt sync`); `container.ts` is the only caller of the `container` CLI (`exec`, `stop`, the runtime's own stop/start) and `liveness.ts` owns the host-side starved-VM verdict; `container-address.ts` owns the addresses a session hands out or dials (VM IP, host gateway, tailnet name); `devvm.ts` mirrors wt's devvm contract (the VM and state paths, the `wt sh` entry script, the workspace user) and sources the workspace environment wt publishes there, so a dev server this session starts already accepts the workspace's own tailnet name, and a workspace wt never published one for is reconciled through `wt sync` without ever blocking routing; VM sizing comes from the project's `.pi/container.json` (2 vCPU / 4 GB here, wt's default, kept by choice), so a starved VM is answered by the host-side verdict and the runtime escalation, never by a silent resize; `bash-ops.ts` owns host-to-guest path mapping and the `BashOperations` adapter, including the two commands that must not run in the VM: a bare `git` goes to pi's local shell (with `HOST_GIT_NOTICE` saying so) because the worktree's `.git` file names a host path the mount does not carry, and a successful host-side `write`/`edit` makes the guest `touch` the file it changed, because virtiofs delivers no event for a host write and an in-VM watcher would never fire. `guest-git.ts` owns the guest's git identity: neither vehicle carries the host's `~/.gitconfig` (the share starts at the worktree's parent, never at the home directory), so activation reads the identity in effect for that worktree through the runtime's own local shell (`sandboxHostOperations()`) and applies it to the guest's global config only where the guest differs - one `git config --get` per key when it already matches, never a rewrite of a repository's own local identity - reporting the single write it made, and failing that step rather than the session when the guest refuses it. `index.ts` also registers both shell tools, and the prompt surface it gives the bash tool is this config's own: `promptSnippet` and `promptGuidelines` are set explicitly because pi's built-in text ("Execute bash commands (ls, grep, find, etc.)", "Use bash for file operations like ls, rg, find") is read at the moment of every call and would otherwise tell the model to do exactly what `tool-guard` refuses. It never creates, names or removes containers, and file tools stay host-side because the worktree is the same bytes through the mount. Liveness is host-side knowledge, never the runtime's `running` state: a failed probe is remembered for minutes so every later call fails at once instead of queueing behind the hang and the best-effort post-edit touch skips, and `/container restart` escalates to the runtime's own stop/start when a starved VM ignores even `stop` - the only lever that answers there, machine-wide, and the notification says so. The addresses a human is given are the workspace's own tailnet ones: `container.ts` reads the node's MagicDNS name once per activation, `sandbox-prompt.ts` turns it plus the project's `tailscale.ports` into the links the prompt requires the model to report, and the VM's localhost stays what only the model's own commands use. `runtime.ts` also owns the boundary's one cross-extension seam: `sandboxBashOperations()` returns the active guest `BashOperations` - the same adapter the bash tool runs, liveness guard, path mapping and failure text included - or null while bash itself runs on the host, and `extensions/dev-server/` consumes it so `dev_server` starts, stops and inspects its server where the project's bash runs instead of on the host. The active runtime is published on `globalThis` under the versioned key `pi.container-sandbox.runtime.v1` rather than held in a module variable, because jiti gives every extension its own module registry: an imported copy of this module would always read an empty runtime and silently fall back to the host. The workspace's context-line link follows the same realm (`pi.container-sandbox.link.v1`): session.ts publishes the workspace's tailnet URL once per activation (`containerLink` - only when the node answers and the project declares the port, as `tailscale.ports` entry or as wt's `tailscale.index`), `clearRuntimeState` drops it on session shutdown, and the footer's context line renders it as its `[container]` segment instead of recomputing per render.
- `ui/pi-runtime.ts` resolves the CLI's actual bundled classes and owns version-drift detection (`detectPiDrift`, `AUDITED_PI_VERSION`); `ui/renderer-drift.ts` mounts the drift warning widget. `ui/pi-component-patch.ts` owns checked method replacement and restoration. Private Pi field/method knowledge stays at the display-surface boundaries; drift never blocks installation — the `pi-updated` skill re-audits the adapters and extensions against the running release.
- `renderers/response-message.ts` classifies response sections using provider phase metadata and message lifecycle, never prose heuristics. `assistant-surface.ts` alone adapts Pi's assistant component, including streaming flags, thinking controls, stop notices and Markdown transformers. It rebuilds independently of the retired raw assistant patch so the first reload can migrate already-loaded classes.
- `ui/response-divider.ts` owns centered response landmarks and fades; `ui/response-markdown.ts` owns readable typography, inset, width bounds and Markdown caching over Pi's parser. `ui/relay-line.ts` colors authored rail glyphs in plain text tokens, not code fences.
- `raw-transcript/` owns literal user prompt frames and the skill invocation callout. `prompt-block.ts` composes attachment content before source text; `skill-block.ts` paints the rose callout band from the parsed skill block and `skill-surface.ts` mounts it on Pi's skill component while retaining the global expand toggle and adding the click-to-fold gesture the native card never had; its rose glow easing to transparent is static paint computed per render, never a timer, and the band owns its own viewport painting instead of Pi's flat custom-message background. `surfaces.ts` preserves that component across native rebuilds and retains prompt zones. `attachment-surface.ts` adapts Pi's entry mounting to move a matching attachment entry into the nearest prompt, retaining native entry invalidation/theme rebuilding without its standalone spacer. `ui/prompt-attachment.ts` is the cross-extension marker/ownership contract; `extensions/attachments/` (no index.ts: shared library) owns the scenario-neutral capture machinery - alias ingestion, editor hooks, thumbnail strip, previews and snapshot records - and `prompt-attachments/` owns only the prompt wiring (draft lifecycle, its session entry, strip widget). The questionnaire reuses the same machinery through `questionnaire-captures.ts`, answering with its own reference rule: its split text (answers, drafts, live editor) retains captures, submits them as multimodal result content and persists tile-sized snapshot records in its details. Assistant content, tool spacing and mouse geometry belong to `renderers/`, so two extensions never patch the same surface.

## State lifetime

- `herdr-prompts/` bridges Pi's `ui_prompt_start`/`ui_prompt_end` spans to the generated integration's own `herdr:blocked` sibling event, so an open questionnaire or dialog reports `blocked` instead of `idle`. It is display-adjacent only: lifecycle state and session identity stay owned by the generated `herdr-agent-state.ts`, which is never modified and never excluded — Herdr accepts lifecycle writes only from the live integration, so no CLI-side reporter can replace it without losing native session restore.

- Each questionnaire dialog owns its editor, navigation state, response collection and render cache. Keyboard events drive mutations on the TUI event loop; render functions only read domain state. The Pi editor computes its own layout during rendering.
- `QuestionnaireResponses` owns answers, drafts and multi-selection sets. Navigation owns the current tab/cursor; selection transitions operate through those owners. Plain snapshots cross the chat-pause boundary.
- The tool registration owns the map of chat-pause snapshots. It deletes a snapshot on completion/cancellation and clears the map on session shutdown, including reload. A chat pause emits `discussing`; reopening emits `answering`. Goal-gate keeps the discussion pause across ordinary user turns, so it cannot auto-relaunch the questionnaire while the user talks.
- Pi owns tool execution, results, images and expansion state. `ToolRow` owns presentation state; `ToolLifecycle` records starts only while execution is actually pending, then freezes completion time. `tool-durations.ts` remembers measured durations in a reload-stable weak cache keyed by result-content identity and call ID. Pi keeps those content arrays during `/reload`, so remounting retains real timings without altering results or writing extra session entries. Freshly loaded history without an observed duration remains unknown. Render methods only read this state; observations and cache writes happen during native display updates.
- `write-snapshots.ts` reads bounded regular-file before-images during `tool_call`, then records successful comparisons at `tool_execution_end` before Pi updates the row. Arguments, results and execution are never replaced. Pending captures clear at agent end/shutdown; a generation check rejects late reads after clearing. Completed views use weak result-content/call-ID keys across reload, without extra session entries. Unknown, binary, oversized or specially normalized baselines fall back to explicitly labeled neutral written content (or native details), never invented removals/additions. Rendering performs no filesystem IO.
- Assistant response dividers and Markdown cache by width and invalidate with their owning message. Streaming rebuilds presentation only; stored messages and provider signatures are untouched. Unknown streaming responses remain neutral until completion; explicit provider phases distinguish commentary and final text even within one message. No response animation timer is introduced.
- One session-scoped `ui/activity-clock.ts` lazily repaints live tool rows, deduplicated per TUI. The final completion stops its pulse; shutdown/reload disposes it and restores the display adapters. Native detail renderers retain separate call/result caches and continue receiving completion after first expansion so their own resources can settle.
- Prompt attachment relocation happens during entry mounting, never during rendering. Session entries and model image content are unchanged; unmatched entries remain visible standalone. Nested entries retain their native invalidation lifecycle, and prompt/attachment display patches restore together on shutdown or reload.
- Questionnaire transcript slots share Pi's row-local answered flag. Their invalidation is queued to avoid synchronous render reentry. Capture pruning runs outside the store's own repaint path: the dialog effects batch prunes once, the strip only invalidates, so a no-op prune never loops a render.
- `prompt-telemetry` owns the prompt it tracks, the activity block it draws in the editor's top border, and its lifetime: the block renders from that state plus the current clock, with no tick timer and no retire timer of its own. Its numbers and tally icons wear the loading color while their words stay muted house ink, its elapsed track carries the prompt border hue, and before the first count the track sweeps the columns the readings will take - so the block reports and waits at one width, and a settled block stays frozen until the next prompt.
- `ui/surface.ts` owns widget registrations and subscriber notifications. `ui/ordered-widget-stack.ts` is the Pi mounting adapter, not another renderer or color system. Both hold their cross-extension state on `globalThis` under versioned `Symbol.for` keys (`pi.ui.surface-registry.v1`, `pi.ui.ordered-widget-bindings.v1`): jiti gives every extension its own module registry, so one above-editor host widget serves the whole process and `ABOVE_EDITOR_PRIORITY` orders every surface in one ladder (`contextLine` 0, `goal` 100, `backgroundTasks` 200, `activity` 300, `attachments` 400). A binding held by a previous session's ui context is stale and remounts under the caller's ui.
- `extensions/footer/context-line.ts` owns the contextual line above the prompt: one line, highest above-editor priority, rendered only while one of its three segments exists - a `[container]` label hyperlinked to the workspace's tailnet URL (read from container-sandbox's link seam), the `[review]` Galley link and the `[PR #n]` link. The footer's line 2 keeps git alone; its statuses group filters the container key (`CONTAINER_STATUS_KEY`) out.

## Boundaries and verification

- `schema.ts` owns every tool-data shape: the LLM input schema and the canonical domain/`details` schemas; UI domain types derive from them via `Static`, so each field has one declared rule set. `normalizeQuestions()` enforces semantic constraints beyond shape (trimming, `Q{i}` fallbacks, uniqueness), and session replay re-validates through the same schemas (`Value.Parse`/`Value.Default`), falling back to plain text when the payload is unusable. Pending streamed previews read only the labels they display.
- Public output is bounded by terminal columns, not JavaScript string length. Editor rendering reserves enough space for a wide grapheme and cursor before the frame clips narrow viewports.
- Regression tests cover multiline/editor alignment, Unicode, styled wrapping, hyperlinks, narrow frames/surfaces, selection markers and footer color interpolation. They use Pi's real editor without starting terminal IO.
- Run the lint, type-check and test scripts from this directory. Format only changed code files. Use `/reload` and a visual questionnaire check after UI changes; automated tests do not establish font-specific appearance.
