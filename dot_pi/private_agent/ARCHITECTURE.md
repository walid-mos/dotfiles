# Custom Pi UI architecture

## Ownership and dependency direction

- `themes/catppuccin-latte.json` owns raw house colors. `extensions/lib/ui/design-system/palette.ts` reads its `vars`; there is no second hex table.
- `extensions/lib/ui/design-system/theme.ts` maps colors to semantic roles and styles. The custom UI intentionally keeps the existing fixed Latte appearance; runtime theme switching is not implemented here.
- `extensions/lib/ui/design-system/terminal-color.ts` owns color parsing, blending and nested ANSI styling. hud-footer quota ramps use the same blending implementation.
- `extensions/lib/ui/terminal-text.ts` owns clipping, wrapping, column slicing and hanging-indent policy. Pi TUI owns Unicode/grapheme measurement and escape parsing; do not maintain another tokenizer or width table locally.
- `extensions/lib/ui/align.ts`, `frame.ts`, and `selection-marker.ts` own shared spacing, rounded/square frames, focused-row bands and selection contrast. Frames compute clipping and padding themselves; callers provide content and spacing insets rather than precomputed width metrics.
- `extensions/lib/ui/editor-decorator.ts` composes per-extension editor decorators exactly once per session_start, chaining on pi's `getEditorComponent`, and owns the base editor factory (`createDefaultEditor`). Only the first registered decorator builds that base editor, and extensions load in filesystem order, so every caller passes this factory instead of constructing its own. Decorators rebind instance methods (the sanctioned adapter hook) and accessor-intercept reassignable callbacks, because pi reassigns `onChange`/`onSubmit` after the editor factory runs; management of that contract lives here, not per extension. A decorator that renders dynamic content also receives the live TUI, so it can request its own repaints. It also owns `EMBEDDED_LOADER_FIELD_WIDTH`, the top-border columns reserved for the embedded loader, so decorators drawing beside the loader lay out against a stable field.
- Questionnaire and hud-footer modules own their domain content and interactions, not parallel UI engines. Every questionnaire choice includes a user-written answer path; the public schema cannot remove it. `ui/ask-user-question/questionnaire-events.ts` is the one cross-extension contract for answer/discussion mode: a questionnaire raised mid-run is the visible stop instead of an injected repeat (the goal-gate continuation machinery that used to suspend around discussions is disabled, see `disabled-extensions/goal-gate/`). Shared `lib/ui/` modules never import extension-specific modules and have no `index.ts` extension entry point.
- `extensions/commands/goal/` owns the active-branch checklist through Pi custom entries. `lib/goal/state.ts` owns storage and projection; `edits.ts` and `manage-edits.ts` own pure transitions; `schema.ts` owns tool input; `tool.ts` and `commands.ts` own entry points; `status.ts`, `widget.ts` and `panel*.ts` own presentation. `route-events.ts` records genuine human input and `routing.ts` owns the agent instructions shared by the human-input notice and tool. Routine declaration, routing and ticks make no remote request. Ticks retain the reported evidence without claiming independent verification; request completion waits for the concrete items. `manage.ts` reserves Jev for destructive delete/revise operations, requiring fresh human input, an unchanged revision and coverage of the requested edit. Missing credentials refuse that operation without disabling local progress. The extension never schedules a turn or sends a synthetic user message. `visibility.ts` owns the global display preference, not branch state. `/goal`, `/goal-widget`, `/goal-clear` and `activate` retain their existing entry points. `commands/context-budget/` reads the same branch snapshot for checkpoints.
- `extensions/commands/dump/` owns the `/dump` snapshot and its ordered above-editor receipt. The receipt retires on the next human-origin prompt; a pending save still finishes copying to the clipboard without remounting a dismissed receipt. `lib/human-prompt.ts` defines which Pi input sources count for this and goal routing.
- `extensions/goal-gate/` — **disabled** (moved to `disabled-extensions/goal-gate/`, kept for reference; its routing and continuation hooks are no longer loaded; the new goal tool is independent). Historically it owned one session ledger and two routing decisions: `task-routing.ts` asks Jev whether a human prompt requests work, then seeds one request item; `tool.ts` passes declared deliverables and explicitly discovered affected surfaces after discovery, using the ledger count as a proposal and Jev as the final direct/scoped reviewer. An uncertain request stays tracked, uncertain scope prefers scoped, and a Jev outage warns visibly while retaining the ledger proposal. `ledger-edits.ts` permits dismissing a false work request only before any deliverable is declared. `routing-log.ts` records hashed prompts, affected-surface counts and decision metadata in per-session files under `jev/routing/` with 14-day retention; raw prompts and surfaces never enter that log. Child subagents do not own goals.
- `extensions/model/fallback/` owns the unified model surface (`/models`): automatic switching applies only to interactive sessions; headless children keep their own model and fallback contracts. `chain.ts`, `fallback-session.ts`, `failover.ts`, `taxonomy.ts` and `config.ts` own recovery decisions. `retry-budget.ts` owns retry credits and plans, `retry.ts` owns retry execution, and `fallback-message.ts` owns the continuation message contract and renderer. `model-catalog.ts` builds the rows from the available catalogue plus the session scope and owns how a saved `enabledModels` entry names a model exactly (pi's colon-suffix rule, bare ids included), the saved-order sort of the scoped group and the fuzzy search every model list filters with (`filterRows`, pi-tui's `fuzzyFilter`), `model-price.ts` owns what a row costs and `model-price-gauge.ts` the gauge, and `openrouter-pricing.ts` owns the live public OpenRouter price list the picker prefers for OpenRouter rows (catalog zeros there mean unpriced, never free); `model-picker-state.ts`, `model-picker-view.ts`, `model-picker-line.ts`, `model-picker-words.ts` (the three names - session, startup default, Ctrl+P list - that every picker surface spells the same way), `model-picker-effort.ts` (the reasoning column all three model lists share), `model-picker-list.ts`, `model-picker-price.ts` (the session tab's price block), `model-picker-scope.ts` (the scope tab's rows, status lines and row-aware footer), `model-picker-tabs.ts` (the fallback and agent tabs), `model-picker-groups.ts`, `model-picker-window.ts`, `model-picker-keymap.ts` (what one terminal key asks for), `model-picker-commands.ts`, `model-picker-scope-edits.ts` (the saved list's membership, removal and order edits, from the scope tab and the session catalogue), `model-picker-editor.ts` (with `model-picker-editor-rows.ts` - the no-model-change row - and `model-picker-editor-render.ts`) and `model-picker-render.ts` hold the pure state and layout (group dividers, the agent editor and row actions included), `model-picker-component.ts` is the pi-tui keyboard/mouse adapter, `command.ts` registers `/models` and owns its status text, and `picker.ts` owns the interactive picker flow. `model-picker-settings.ts` reads the settings the `subagents` package owns and writes back exactly two things: the inline editor's model and thinking (or the agents list's thinking alone) for one agent in `subagents.agentOverrides`, and the saved `enabledModels` list - its membership and its order - both as whole-file read-modify-write (`model-picker-settings-file.ts` owns the file's own indentation and the atomic replace) with unrelated keys preserved, and a refusal when the list another writer owns changed underneath; `model-picker-saves.ts` turns agent pins, the checkpoint model and the startup default into notices that state when each takes effect; a successful Ctrl+P-list edit notifies nothing, because the picker's own rows moving between the saved and available groups are the feedback, and a refused edit reports why. `agent-roster.ts` asks the installed `subagents` package for its agent roster over pi's in-process event bus (`pi-subagents:agent-roster:v1`, produced by that package's own discovery) and validates the plain-JSON answer field by field, so the agents tab lists every agent that can be pinned - each row naming its effective model and whether that model is a pin, the agent's own definition, `subagents.defaultModel` or the session's - while a pin left behind by an agent that no longer exists is listed and marked instead of silently doing nothing, and a package that does not answer leaves the picker on the pins it can read itself. The Ctrl+P list tab (labelled `ctrl+p`) lists the entries once with what each resolved to, each row saying `Ctrl+P list`, `in Ctrl+P list via <pattern>` or `not in Ctrl+P list`: enter toggles membership - an exact entry leaves the list, any other model joins it as its own exact entry (a model a saved pattern covers is pinned explicitly, never expanded out of its wildcard) - backspace removes an entry, a wildcard included, as one whole entry the footer labels, and alt+up/down orders the list. The session catalogue's enter adds the highlighted model to that same saved list as its own exact entry and ctrl+x removes that entry again - so a scope can be built from the default picker that has no entries at all - and its ctrl+s saves the highlighted row as pi's startup default (`defaultProvider`/`defaultModel`, the keys pi's own `/model` picker writes with that key), which is a write of its own that names new sessions and leaves the running one on the model it is on; a row the saved list already covers - an exact entry, or a pattern that matches it - is one this session can run, so enter there switches the session model instead, and the row says `in Ctrl+P list` or `in Ctrl+P list via <pattern>`. A row only a pattern covers has no exact entry to remove, so ctrl+x leaves that edit to the scope tab's explicit backspace. Every editing key is a control key (enter, ctrl+x, ctrl+s, backspace) and the session search field owns every printable character: `space` and every letter stay text, so a model id like `codex` or `x-ai/grok` is searchable to its last character. `enabledModels` is pi's own setting, pi re-resolves the scope on every session start (`/new` and `/resume` re-run the runtime and re-read settings.json, so no pi relaunch is ever needed), and no extension API can move the running session's scope (`ctx.scopedModels` is a read-only snapshot and the extension runtime context carries no setter), so the scope tab says an edit applies when pi starts its next session (a `/new` now) and the picker's session list reacts immediately without faking a runtime mutation: the rows follow the saved `enabledModels` order, and a model the saved list names exactly (and this session's own scope does not cover) leaves the `available` rest for the `in Ctrl+P list next session` group the moment the key is pressed - `in Ctrl+P list now` (usable now), `in Ctrl+P list next session` (wanted from the next session on, tagged `not cycling now  in Ctrl+P list`), `available` - so nothing needs a relaunch to show up in the right list, while the session scope itself still moves only when pi starts a session. A saved wildcard moves whole, is never expanded into ids and is never rewritten by a membership toggle. `/scoped-models` remains pi's own built-in interactive command for the same list - the tab names it instead of pretending to open it, and `command-filter.ts` keeps it, `/model` and `/thinking` out of the slash menu, as it does pi's bundled `llama`, which answers nothing here with no llama.cpp router configured, since pi hardcodes its built-ins and exposes no unregister API: `/models` is the only model entry there, and a hidden command typed out in full still runs; The agents tab has no duplicate `/subagents` launcher; a separately grouped `/context-budget` row edits the checkpoint model through the same inline catalogue editor, without creating a subagent pin or changing `/dump`. The agents tab shows every agent the `subagents` package reports - its effective model and reasoning column, where left/right writes that one agent's thinking and enter or a click opens the model editor - and keeps a pin whose agent no longer exists visible, marked `no such agent`, so it can be repointed; reasoning levels always come from pi's `getSupportedThinkingLevels` and are clamped by pi's `clampThinkingLevel`, so a model that cannot disable reasoning never advertises off and a non-reasoning model reads as off rather than an invented auto; the inline editor offers the models the `enabledModels` list names (exact entries and every row one pattern covers; the whole catalogue when there is no list or the settings file cannot be read) and opens on the pinned model, or on an explicit no-model-change row when the override has no row to sit on (a stored thinking level alone, or a pin whose model its rows do not name), shows a stored level the pinned model no longer accepts, marked `unsupported` (a width-safe `!` marker when the column is too narrow for the word), and a save that changes nothing writes nothing. Escape in the picker is one level back at a time (search, open editor, committed row action, then close), and the footer states which one is next.
- `extensions/ui/hud-footer/inco-session.ts` is the config's browser-session boundary: Inco publishes no balance API, so it replays the console session of the machine (Clerk handshake plus the console layout's flight payload). `quota-inco.ts` parses that payload (pure, fixture-tested); `safari-cookies.ts` owns the macOS Safari cookie format and is the only browser-cookie reader. The read is the Inco console's store; sessions are read, never written, and nothing here runs from a render path.
- `extensions/tools/guard/` owns the tool-call guard rails. `managed-bash.ts` registers bash execution and job controls through Pi's public extension API; `bash-jobs.ts` owns live session jobs, admission limits and bounded waits; `bash-job.ts` owns one execution and its private temporary receipt; `bash-job-schema.ts` owns inputs, states and limits. A foreground deadline promotes the same running command instead of restarting or killing it. Cancel before promotion stops that command; cancelling a later wait leaves the job alive. Session shutdown aborts owned jobs with bounded cleanup, and saved receipts never become live handles after reload. Native Pi owns process-group cancellation, output accumulation and command lifetime timeouts. Completion sends one session-scoped follow-up, never per-chunk model calls; cancellation does not restart the agent. Waits remove settlement listeners on every exit, and finished records are evicted by completion time independently of receipt writes. The bash tool's own actions remain usable in restricted children without granting another tool. This bounds model-issued bash waits, not `!` shell input, `pi.exec`, MCP calls or a blocked JavaScript event loop. Explicit shell detachment and forced Pi termination can leave descendants outside live job control; no in-process shutdown hook can run after SIGKILL. Temporary receipts are evidence, not a persistent job service. Its bash spawn hook removes `HERDR_ENV` from child environments, so a nested interactive Pi cannot advance the parent's Herdr report sequence; pane and socket context stay available for CLI control. Shell lookups: `shell-guard.ts` directs file lookups to dedicated tools; `shell-segments.ts` recognizes literal lookup-only stages, including `cd` setup and output filters, without treating every pipe as exempt. Transformations, storage and unsupported shell syntax remain shell work. `command-evidence.ts` saves recognized validation runs to private temporary logs before display filters and stores their upstream/shell exit status in branch entries; filters read the completed log so `head` cannot truncate the validation. `command-workspace.ts` supplies a bounded, best-effort Git/environment fingerprint for repeat warnings, never a cache hit or proof of unchanged external inputs. `lib/command-evidence/schema.ts` owns the shared record and checkpoint read-back. Read dedup: `read-ledger.ts` persists bounded file/range/signature and result-hash metadata. It refuses only while the exact successful source result remains in projected model context; changed files, dropped results and rewritten results permit rereading. Genuine human input clears the request ledger; navigation restores that branch.
- `extensions/tools/lazy-load/` owns the session's own active-tool set: which tool schemas a UI session starts without, and the `load_tools` loader that brings one back. `policy.ts` holds the pure plan (config layers, `defer` and `off`); `index.ts` only wires `session_start` and the loader's activation. It scopes UI sessions (`ctx.hasUI`) and never headless or granted sessions, so a subagent child keeps the set its caller granted; tool-guard respects the active set without changing it.
- `extensions/commands/simplify/` owns the `/simplify` command: explicit scopes stay deterministic, while `target-routing.ts` asks Jev whether a bare target is a literal file area or a semantic request; uncertain/unavailable decisions and failed literal lookups use `target-message.ts` to hand the entire request to the parent agent for per-unit planning and execution (existing checkout only, commit only when requested). The deterministic path runs four fresh-eyes lenses through the installed subagents package, an autonomous pass over provable Git-scoped findings, a human checkpoint for the rest (all direct-target findings included), and the project's own gates after every edit. `index.ts` is wiring only (registration, preflight, notices) and `pipeline.ts`/`pipeline-apply.ts` are the two stages; `command-args.ts` parses flags and free target text while `command-help.ts` owns its help; `git-shell.ts` is the only process boundary, `git-selection.ts` decides which files each mode yields, `git-snapshot.ts` resolves a bare target or explicit `--files`/`--snapshot` roots without Git and recursively excludes dependency/build directories, `git-files.ts` owns the per-file facts (ranges, size, binary/submodule checks, content hash), and `git-scope.ts` assembles the manifest under caps (200 files, 4096 ranges) that refuse rather than truncate; `lenses.ts` owns the four lens tasks, the findings schema and the serial, tool-budgeted workflow it writes for the parent model to launch by path, plus its workflow spend budget. Failed children are reported without automatic structured-output recovery; `turns.ts` resolves a dispatched run on `agent_settled` (never on `waitForIdle` ordering); `capture.ts` reads the `subagent` tool result defensively, field by field; `findings.ts` validates, scope-filters, deduplicates and ranks what the lenses returned, and drops findings whose file changed under it; `verify.ts` detects the project's gates; `apply.ts` carries the behaviour-preservation and verification contract; `select-ui.ts` is the checkpoint dialog; `report.ts` is the notices. The extension never edits code, runs a gate or stages anything: the model does that through its own tools, and the lens children are read-only by contract (`agents/simplifier.md`). The semantic-target handoff asks the parent to apply the same lens and verification contracts per unit, and permits commits only when the user's directive explicitly requests them. The manifest anchors reviewed problems rather than limiting their supporting edits; `apply.ts` owns those edit bounds and the all-changed-files report. Independent out-of-scope observations are reported as notes, every dropped finding carries its reason, and a missing or unusable lens result is a reported failure rather than an empty finding set.
- `packages/subagents/` is the vendored `pi-subagents` package (the `subagent`, `bg_wait` and `subagent_supervisor` tools, the agent roster event, workflows), loaded through `settings.json` `packages`. Read its `FORK.md` before changing it: the history lives in `~/Development/tools/pi-subagents` and `SOURCE.md` names the vendored commit. It keeps its own `package.json`, `node_modules`, tests and gates (`pnpm run typecheck`, `test`, `test:integration` run there), so the root lint and format ignore `packages/**`; its config file stays `extensions/subagent/config.json`.
- `extensions/commands/context-budget/` owns context growth. `growth.ts` checkpoints at completed tool batches without injecting a continuation. Failure warns once and leaves work running; automatic attempts resume after human input or a changed limit/model. `preparation.ts` uses the edited projection, keeps tool pairs together and preserves historical file metadata; `prompt.ts` scopes claims to the summarized prefix, retains the current goal and prior checkpoint, and excludes assistant reasoning. `current-state.ts` adds bounded observed command evidence from the full edited projection and branch receipts; missing evidence never means a command did not run. `summary.ts` prefixes a deterministic scope notice and calls only the configured model with bounded output and deadline. Pi auto-compaction stays disabled, native threshold/overflow attempts are refused, and no native-summary fallback exists. `/context-budget` opens `limit-picker.ts`, using Pi Input/SelectList and the house frame; `choices.ts` owns presets, numeric parsing and labels. `status` reports usage, `192k` or `192000` saves directly, and `checkpoint` requests the custom summary. `lib/context-budget/model.ts` owns the validated settings, model-window cap and synchronous model save; `lib/context-budget/events.ts` owns the `context-budget:saved.v1` bus channel, fired after every save so the hud-footer gauge rereads the file; `budget-writer.ts` queues budget writes, prepares unique temporary files asynchronously, then checks and renames without yielding to another in-process writer. Permissions and unrelated keys are retained. A saved limit applies at the next completed batch, including during generation; opening the menu never waits for idle or aborts work. Pi supplies durable storage and projection, not the growth policy. `disabled-extensions/context-budget/` is inactive historical code, not a second controller.
- `extensions/lib/settle-handshake/` (no index.ts: shared library) is retired and has no active consumers. Historically it owned the cross-extension contract on the settle boundary: `context-budget` claimed it while threshold or recovery compaction was pending, and `goal-gate` deferred continuations without spending its attempt budget; with both disabled the claim currently has no takers. Completion, failure, cancellation, any compaction and session start release the claim; a TTL self-heals a wedged cycle. Extensions load in filesystem order, so the claim makes compaction-before-continuation explicit instead of relying on `ctx.isIdle()`, which cannot arbitrate handlers within one settle dispatch.

Edit/write and any result carrying native images use standalone panels on the shared content column, with a dedicated inline/expanded code view for applied changes; other expanded content stays with the originating tool extension.

## Herdr task names

`extensions/herdr/task-names/` owns task-based sidebar and tab names. `service.ts` runs inside interactive Pi sessions, never as an OS service. `ownership.ts` elects one writer per Herdr socket using an identity-checked localhost port; the kernel releases ownership after a crash, and other panes retry. Shutdown aborts and drains pending naming before releasing ownership. Only the elected Pi session writes automatic names and socket-scoped state under `~/.config/herdr/task-names/`. `tasks.ts` reads declared goals on live Pi session branches, excluding inspectors without their own goals from tab summaries. `index.ts` starts and stops the in-process coordinator with Pi's session lifecycle, publishes live branch selections and provides `/tab-name <name|auto>`. `summarize.ts` sends declared checklist text only to the configured model. `stable-titles.ts` preserves exact titles for unchanged tasks. `coordinator.ts` ignores focus and activity, prefers unfinished pane goals, rejects stale model results and preserves observed manual tab names until an explicit auto request. Manual pane labels take precedence in the sidebar. Without a declaration, the sidebar says `No declared task`; before a summary arrives it displays the first declared item. Tabs without declared work use their workspace name, and obsolete automatic titles clear before a model call, including on naming failures. The coordinator reads persisted branches for already-running panes; `/reload` activates the lifecycle hooks, branch-navigation reporting and command. Herdr's generated integration files and Pi session journals remain untouched. The portable model setting lives in `herdr-task-names.json` under Pi's agent directory. Usage goes to socket-scoped `naming.log`; failures produce a deduplicated Pi notification. `HERDR_BIN_PATH` selects Herdr when available. No machine-specific executable paths, launchd files or detached worker processes are needed.

## State lifetime

- `herdr/prompts/` bridges Pi's `ui_prompt_start`/`ui_prompt_end` spans to the generated integration's own `herdr:blocked` sibling event, so an open questionnaire or dialog reports `blocked` instead of `idle`. It is display-adjacent only: lifecycle state and session identity stay owned by the generated `herdr-agent-state.ts`, which is never modified and never excluded — Herdr accepts lifecycle writes only from the live integration, so no CLI-side reporter can replace it without losing native session restore.

- Each questionnaire dialog owns its editor, navigation state, response collection and render cache. Keyboard events drive mutations on the TUI event loop; render functions only read domain state. The Pi editor computes its own layout during rendering.
- `QuestionnaireResponses` owns answers, drafts and multi-selection sets. Navigation owns the current tab/cursor; selection transitions operate through those owners. Plain snapshots cross the chat-pause boundary.
- The tool registration owns the map of chat-pause snapshots. It deletes a snapshot on completion/cancellation and clears the map on session shutdown, including reload. A chat pause emits `discussing`; reopening emits `answering`, and the questionnaire is never auto-relaunched while the user talks.
- Pi owns tool execution, results, images and expansion state. `ToolRow` owns presentation state; `ToolLifecycle` records starts only while execution is actually pending, then freezes completion time. `tool-durations.ts` remembers measured durations in a reload-stable weak cache keyed by result-content identity and call ID. Pi keeps those content arrays during `/reload`, so remounting retains real timings without altering results or writing extra session entries. Freshly loaded history without an observed duration remains unknown. Render methods only read this state; observations and cache writes happen during native display updates.
- `write-snapshots.ts` reads bounded regular-file before-images during `tool_call`, then records successful comparisons at `tool_execution_end` before Pi updates the row. Arguments, results and execution are never replaced. Pending captures clear at agent end/shutdown; a generation check rejects late reads after clearing. Completed views use weak result-content/call-ID keys across reload, without extra session entries. Unknown, binary, oversized or specially normalized baselines fall back to explicitly labeled neutral written content (or native details), never invented removals/additions. Rendering performs no filesystem IO.
- Assistant response dividers and Markdown cache by width and invalidate with their owning message. Streaming rebuilds presentation only; stored messages and provider signatures are untouched. Unknown streaming responses remain neutral until completion; explicit provider phases distinguish commentary and final text even within one message. No response animation timer is introduced.
- One session-scoped `lib/ui/activity-clock.ts` lazily repaints live tool rows, deduplicated per TUI. The final completion stops its pulse; shutdown/reload disposes it and restores the display adapters. Native detail renderers retain separate call/result caches and continue receiving completion after first expansion so their own resources can settle.
- Prompt attachment relocation happens during entry mounting, never during rendering. Session entries and model image content are unchanged; unmatched entries remain visible standalone. Nested entries retain their native invalidation lifecycle, and prompt/attachment display patches restore together on shutdown or reload.
- Questionnaire transcript slots share Pi's row-local answered flag. Their invalidation is queued to avoid synchronous render reentry. Capture pruning runs outside the store's own repaint path: the dialog effects batch prunes once, the strip only invalidates, so a no-op prune never loops a render.
- The `hud-` prefix names the chat's passive status layer - everything pi's chat shows around the conversation: `extensions/ui/hud-status/` (working label below the chat), `extensions/ui/hud-telemetry/` (editor-border telemetry block), `extensions/ui/hud-footer/` (status lines and the context line). The hud-footer's line 2 context gauge merges the Context Budget: one 12-cell bar over the model window on a shared sqrt-warped cell axis (small shares keep latitude, shares beat 0→0 and 1→12 monotonically) with the usage fill on the left and the budget band after the budget's warped cell - one bright wall cell at the wall and fade-to-horizon cells from there to the bar's end, bounded at 4 cells, solid diamonds blending the budget hue toward the base so the band never reads as usage (the usage ramp never wears these hues; the effective model cap and the clamps keep the wall inside the bar; the limit token wears the quiet band-hued ink in the full lane; `ui/hud-footer/budget.ts` reads the cached settings), and no plain-text context-budget footer status exists. A new chat-status extension takes the same prefix; interactive input surfaces (questionnaire, attachment strip) do not.
- `hud-telemetry` owns the prompt it tracks, the activity block it draws in the editor's top border, and its lifetime: the block renders from that state plus the current clock, with no tick timer and no retire timer of its own. Its numbers and tally icons wear the loading color while their words stay muted house ink, its elapsed track carries the prompt border hue, and before the first count the track sweeps the columns the readings will take - so the block reports and waits at one width, and a settled block stays frozen until the next prompt. Its timing modules also store measured provider, tool, instrumented-hook and compaction durations with provider-reported cache usage. `timing-wiring.ts` owns event registration and persistence; `timing-collector.ts` reopens measured activity at agent/provider/tool boundaries after native async wakes and exposes a non-settling snapshot. `timing-requests.ts`, `timing-tools.ts` and `timing-compactions.ts` own interval accounting; `timing-book.ts` assembles records. `timing-records.ts` owns the versioned entry contract and `timing-totals.ts` owns aggregates that survive detail-row caps. `timing-entry.ts` and `timing-entry-values.ts` validate storage; `timing-view.ts` includes current in-memory measurements in `/latency`. `lib/telemetry/hook-timing.ts` owns the bounded cross-extension hook channel and complete aggregate count/duration. Unobserved durations remain unknown.
- `lib/ui/surface.ts` owns widget registrations and subscriber notifications. `lib/ui/ordered-widget-stack.ts` is the Pi mounting adapter, not another renderer or color system. Both hold their cross-extension state on `globalThis` under versioned `Symbol.for` keys defined in their owning modules. Bump the key when its stored contract changes, because `/reload` preserves process globals: jiti gives every extension its own module registry, so one above-editor host widget serves the whole process and `ABOVE_EDITOR_PRIORITY` orders every surface in one ladder (`contextLine` 0, `goal` 100, `backgroundTasks` 200, `activity` 300, `attachments` 400). A binding held by a previous session's ui context is stale and remounts under the caller's ui.
- `extensions/ui/hud-footer/git-tracking.ts` owns live Git refresh: one abortable local status read at a time, idle polling plus coalesced tool/branch nudges, changed-snapshot repaints only, and cleanup on footer disposal or shutdown. `git-data.ts` collects branch, upstream counts, working-tree counters and stash in the same read without index writes or network fetches; the footer uses that snapshot's branch rather than mixing independently cached values. `poll-pace.ts` owns the cadence. Headless sessions do not start footer polling.
- `extensions/ui/hud-footer/context-line.ts` owns the contextual line above the prompt: one line, highest above-editor priority, rendered only while a `[review]` link to this Pi session's attached live Syneva desk or a `[PR #n]` link exists. `syneva-data.ts` resolves the saved attachment rather than assuming the reviewed repo matches the Pi cwd. The hud-footer's line 2 keeps git alone.

## Boundaries and verification

- `schema.ts` owns every tool-data shape: the LLM input schema and the canonical domain/`details` schemas; UI domain types derive from them via `Static`, so each field has one declared rule set. `normalizeQuestions()` enforces semantic constraints beyond shape (trimming, `Q{i}` fallbacks, uniqueness), and session replay re-validates through the same schemas (`Value.Parse`/`Value.Default`), falling back to plain text when the payload is unusable. Pending streamed previews read only the labels they display.
- Public output is bounded by terminal columns, not JavaScript string length. Editor rendering reserves enough space for a wide grapheme and cursor before the frame clips narrow viewports.
- Regression tests cover multiline/editor alignment, Unicode, styled wrapping, hyperlinks, narrow frames/surfaces, selection markers and hud-footer color interpolation. They use Pi's real editor without starting terminal IO.
- Run the lint, type-check and test scripts from this directory. Format only changed code files. Use `/reload` and a visual questionnaire check after UI changes; automated tests do not establish font-specific appearance.
